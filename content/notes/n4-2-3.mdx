## 原則

- 要求はステークホルダーが望むこと、要件はそれを開発側が実現可能な形に落とし込んだもの。
- 機能要件と非機能要件は同じくらいの重みで扱う。
- 制約条件は早い段階で洗い出す。踏まえずに積み上げると、「法的にNGだった」と一からやり直すことになる。

## 要求と要件

「もっと使いやすくしたい」という要求は抽象的。これを「ログインボタンを目立つ位置に配置し、1クリックでログインできるようにする」という具体的な要件に落とし込むのが要件定義の仕事。

## なぜ要件定義をするのか

| 目的 | 内容 |
| --- | --- |
| ビジネス価値の最大化 | 高機能でもビジネス目標や顧客ニーズに合わなければ成功ではない。必要最低限でも大きなメリットがあれば価値がある。何が価値に直結するかを見極める |
| 予算・スケジュールの最適化 | 機能が明確になれば工数の見当がつく。優先度が分かれば、スコープ調整のときに最初に作るべき機能を判断できる |
| 変更リスクの軽減 | 合意しておけば核となる要件は簡単に変わらず、変更があっても影響を抑えられる |
| ステークホルダーの満足 | ユーザーは欲しい機能と品質を確認でき、開発者は何を作ればよいかが分かる。無駄な試行錯誤が減る |

## プロセス：要件を定義する

<Steps>
  <Step title="ビジネス要件・コンセプトを把握する">提示された要求や企画、顧客ニーズを整理し、「そもそも何を実現したいのか」をつかむ</Step>
  <Step title="ステークホルダーにヒアリングする">関係者を特定し、それぞれの視点で要望や期待、制約条件を漏れなく集める</Step>
  <Step title="要件を整理する">機能要件・非機能要件・制約条件に分け、優先度をつける</Step>
  <Step title="レビューして合意する">全員からフィードバックをもらい、認識の齟齬や誤解を取り除いて「これで進める」形に仕上げる</Step>
  <Step title="文書化する">後工程で参照しやすく、新メンバーのオンボーディング資料にもなる。変更要望が出たときに、どこを直すべきか判断しやすい</Step>
</Steps>

## 要件の種類

| 種類 | 内容 | 例 |
| --- | --- | --- |
| 機能要件 | システムが何をできるか。操作、処理、画面表示、データの入出力 | 商品検索、在庫管理システムとの自動連携 |
| 非機能要件 | 裏側でシステムが守るべき水準。性能、拡張性、セキュリティ、可用性、運用・保守性 | 処理速度、ダウンタイムの許容範囲、セキュリティ基準、UI・UXポリシー |
| 制約条件・前提条件 | 法規制、業界ルール、技術的な制限 | 個人情報保護法への対応、他システムとの連携仕様、使えるフレームワークや言語 |

## 要件を分類する軸

要件定義では、機能・性能・操作性・デザイン・法律・費用やスケジュールと、多岐にわたる要求が出てくる。営業は早く安く、技術は高品質に、経営層は投資対効果と法的リスクを、というように部門ごとに求めるものも違う。分類すると、優先度の可視化、担当分担の明確化、スコープ管理、抜け漏れ防止がしやすくなる。

| 軸 | 分け方 |
| --- | --- |
| 視点 | ビジネス（事業戦略、収益モデル、ブランド価値）／運用（メンテナンス性、管理体制、障害対応）／ユーザー（UI/UX、満足度、利便性） |
| 機能種別 | 基幹機能／サブ機能／管理系機能／連携機能（API連携やデータ連携） |
| 品質特性 | 機能適合性、信頼性、性能効率性、互換性、使用性 |
| 制約 | 予算・人員・スケジュール／法的要件・規制（個人情報保護法、GDPR）／技術制約／運用ポリシー（セキュリティルール、バックアップ、障害対応） |

必要に応じて複数の軸を重ねてマトリクスにすると、抜け漏れを防げる。誰がどの要件を出したのか、出所も明確にして意見の対立をコントロールする。

<Note title="事例：小売チェーンのポイントアプリ">ポイント残高確認、クーポン配布、新商品予約、店舗在庫のリアルタイム連携は機能要件。ブランドカラーへの準拠、多要素認証、秋のキャンペーンまでのリリース、スケールアウト対応は非機能要件や制約。視点で見ると、クーポンと予約は販促や売上拡大（ビジネス）、在庫連携とスケールアウトは運用、残高確認と多要素認証は満足度と安心感（ユーザー）につながる。</Note>

## 分類するときの注意点

<Cards>
  <Card label="分類しすぎない">あらゆる観点で細かく分けると、かえって複雑になり共有も難しくなる。分類は合意形成と抜け漏れ防止の手段</Card>
  <Card label="相手の理解度を考える">クライアントがITに詳しいとは限らない。「これは非機能要件で」と専門用語で一方的に説明しても伝わらない</Card>
  <Card label="フェーズごとに更新する">要件は進むにつれて変わり、追加・削除される。技術的制約や予算の都合で要求を切り捨てる場面もある</Card>
</Cards>

## 成功のポイント

<Cards cols={2}>
  <Card label="ステークホルダーを巻き込む">現場のスタッフ、最終顧客、運用チームなど、実際に成果物に触れる人の意見を入れる。最終的な意思決定者を最初に明確にする</Card>
  <Card label="背景を掘り下げる">なぜその機能が必要か、どんなユースケースか、実装後にどんな効果を期待しているか。ビジネス的な意図を理解すると、より良い解決策が見つかる</Card>
  <Card label="正確に文書化して共有する">漏れや曖昧さがないようにする。成果物は要件定義書、ユースケース・ユーザーストーリー、非機能要件一覧、制約条件一覧</Card>
  <Card label="ユーザー視点を忘れない">開発側の都合で決めず、使いやすさと価値を意識する。ユーザーストーリーをベースに整理するのが有効</Card>
</Cards>

## 開発手法による違い

| 手法 | 要件定義の進め方 |
| --- | --- |
| ウォーターフォール | 要件定義に十分な時間をかけて凍結し、設計・実装に入る。要件が明確な大規模プロジェクトに向くが、変更に弱い |
| アジャイル | 必要最低限をスピーディに定義し、スプリントを回しながらプロトタイプやフィードバックで具体化・修正する。変化しやすい環境に柔軟に対応できる |
