## 原則

- <Mark>**機能ではなく、課題から考える。ほしい機能ではなく「目的」を聞く。本当に解くべき課題がそこにある。**</Mark>
- 課題とユーザーの仮説が、最初のまま進むことはほぼない。解像度が高いほど、頭の中のイメージと現実のギャップは小さくなる。
- PMがリリース期から成熟期まで見届けられる機会は少ない。どれか1つのフェーズで価値を発揮すれば良い。

| | リリース期 | グロース期 | 成熟期 |
| --- | --- | --- | --- |
| 大事なこと | 最も大きな課題を持っている人を特定する | 課題をより深く解決する。課題に手を広げすぎない。競合にリプレイスされない | まだ解決できていない課題に取り組む。競合にリプレイスされない。余計な機能を追加しない |
| 候補者 | 課題を持つ層を具体的にMECEに分け、各セグメントから選ぶ | 最もプロダクトを利用しているユーザー。可能なら使っていないユーザーも | 過去の要望をまとめてグルーピングし、要望を出したユーザーを選ぶ |
| 確かめること | 課題の大きさ、解決できていない原因、目指したい状態 | なぜ使ってくれるか、どれくらい課題解決できているか、想定外の使い方 | 今のプロダクトで解決できない課題、それを解決したい理由、自社で解決したい理由 |

## リリース期

ユーザーのセグメントをできるだけ具体的にMECEに分類し、その中で誰の課題が大きいかを知ることから始める。課題を持つセグメントを特定したらSuper Specific Whoを決め、「最も大きな課題を持っている人」まで特定する。

<Note title="目安">セグメントの例（PM School）：IT企業で自社ソフトウェア事業あり／IT企業で自社事業なし（SIerなど）／非IT企業で上場している老舗企業／非IT企業で上場していない大企業／ITスタートアップ／非ITスタートアップ。各セグメントで最低2〜3人に聞く。</Note>

候補者は、プロダクトのLPや営業資料の公開、少額の広告、SNSでの募集、知人の紹介で集める。課題があれば候補者は集められる。集まらない場合は、課題がそもそもあるかを再検討する。

### 聞くこと

| 項目 | 質問例 |
| --- | --- |
| 課題の大きさ | 現在抱えている最大の課題は？ どのくらいの頻度で起きる？ 解決されないとどんな影響がある？ 解決のためにどんな方法を試し、どれくらいの時間や労力をかけた？ |
| 解決できていない原因 | まだ解決できていない主な理由は？ 試した方法のどこがうまく機能しなかった？ 既存のツールにどんな障壁や制約がある？ |
| 目指したい状態 | 解決したらどんな効果が期待できる？ どのくらいの予算や期間が妥当？ 成功基準は？ |

何よりも大事なのは課題のファクト。課題の大きさを測るカギは、過去に解決のために行動した内容。行動していなければ、課題が大きくないか優先度が高くない可能性がある。

<Note title="補足">既にプロダクトを導入している場合は、それで解決しきれていない理由が大事。解く課題が同じならリプレイス、違うなら共存になる。競合だけでなく、解決のために使ったツールはすべて把握する。目指したい状態は補足情報にとどめる。ユーザーは課題が解決された状態を正しく理解できているとは限らない。「なぜその解決策がほしいのか」の背景を知る。ユーザーのことをユーザーより知る、カスタマーマニアになる。</Note>

### 実施後

1. 議事録を整理し、チーム全体に共有する場を設ける
2. 課題の仮説と現実のずれを確かめる
3. 課題の共通点をグルーピングする：大きな課題ほど複数社が共通して持っている。言葉は違っても起きている問題は同じことが多い
4. 課題の原因を考察する：ユーザーに原因を聞いても良いが、本当の原因かは分からない。原因を間違えると解決策も間違える
5. 作るべき機能のアイデアを出す：課題と原因を特定して初めて、解決する機能を考える

## グロース期

PMFを達成したプロダクトは選択肢が増えて迷いやすい。このフェーズで最適な判断をすることがPMの大事な仕事。

<Steps>
  <Step title="最も利用しているユーザーを選ぶ">使っているのは、何かしら課題を解決できているから</Step>
  <Step title="セグメントで特徴を分類する">よく使うユーザーの特徴にヒントがある</Step>
  <Step title="5名以上をMECEに選ぶ">セグメントごとに分けて5名以上に聞く</Step>
</Steps>

### 聞くこと

| 項目 | 質問例 |
| --- | --- |
| なぜ使ってくれるか | 使い始めたきっかけと決め手は？ なぜ今も使っている？ どの点に一番価値を感じる？ 他のプロダクトとの違いは？ |
| どれくらい課題解決できているか | 達成したいゴールは？ 解決しきった状態を10段階で測ると今いくつ？ 足りないと感じることは？ 不満や煩わしい操作は？ |
| 想定外の使い方 | 実際に使っているところを見せてください。いつ、どんなときに最も使う？ よく使う機能ベスト3とその理由は？ |

なぜ使っているかが、プロダクト改善の最も大きなヒントになる。明確な回答が得られなくても良い。ヒアリングだけで足りなければ、データ分析と併用して定性・定量の両方を分析する。

<Caution>追加してほしい「機能」を聞いてはいけない。「CSVエクスポート機能がほしい」と言われたら「何をするためですか？」と聞く。「他ツールとの連携のため」なら、API連携など別の解決策も考えられる。</Caution>

機能があることと、使えることは別問題。ユーザーが「機能に気付かない」「機能はあるが使いにくい」「使ってみたが課題解決できない」のどれかで、作るべき・改善するべき機能が変わる。この情報があると優先順位をつけやすい。

<Note title="補足">グロース期のヒアリングは単発ではない。メールやチャット、アンケートで気軽に依頼できる関係とチャネルを作る。ギフト券や現金を渡すとそれ目的の人が出てくる。無料でも協力してくれるユーザーこそ大事な人たち。</Note>

### 実施後

議事録の共有、共通する課題のグルーピング、機能のアイデア出しに加えて、機能の優先順位をつける。作るべき機能は、課題の大きさと、それをどれくらい簡単に解決できるかで決める。機能の優先順位づけは、課題の優先順位づけのこと。優れた機能アイデアとは、できるだけ簡単に解決できるもの。時には機能以外で解決するべきこともある。

## 成熟期

これまでの組織の強みが活きるフェーズ。課題を深く解決しつつ、今まで解決してきた課題の周辺にある新たな課題を見つける。進め方はリリース期と同じで良く、ユーザーが多い分ゼロから立ち上げるより有利に進めやすい。

### 聞くこと

| 項目 | 質問例 |
| --- | --- |
| 今のプロダクトで解決できない課題 | 過去にセールスやCSに出した要望は？ まだ解決できていないものは？ そのためにどんな行動をし、お金や時間をどれくらいかけた？ |
| 解決したい理由 | その課題が重要な理由は？ 解決できないとどんな影響がある？ 最も解きたいと思っているのは誰？ |
| 自社で解決したい理由 | なぜ弊社プロダクトで解決したい？ 他に使っているプロダクトは？ 期待したいことは？ |

セールスやCSと連携して要望を洗い出すことから始める。要望を出すのは、課題があって解決できていない状態。今解いている課題と領域が近いので要望に挙がりやすく、まだ解決できていない大きな課題は新しいプロダクトのチャンスになる。

### 実施後

1. 議事録を整理しチームに展開する
2. 共通する課題をグルーピングする
3. シナジーのある課題を決める：プロダクトビジョンと事業シナジーから選ぶ（例：営業とCS、名刺管理と営業、労務とタレント管理）
4. 新規プロダクトか新機能かを決める：目的は新しい売上だけでなく、既存プロダクトの強化

<Note title="補足">ソフトウェアはプラットフォーム化戦略を取ることが多い（Salesforce、Sansanの名刺管理から営業DX、マネーフォワードの会計領域マルチプロダクトなど）。競合がいるから諦めるのではなく、競合に満足していない点もチャンスとしてフラットに探る。新規プロダクトの立ち上げは本来事業開発のスキルだが、PMに期待されることも多い。</Note>

## 開発段階ごとの聞き方

| 段階 | 目的 | 質問例 |
| --- | --- | --- |
| アイデア・課題探索 | 課題や生活・仕事環境を深く理解する | 最近、不便だと感じたことは？ 今はどんな工夫をしている？ 理想の状態は？ |
| コンセプト・初期プロトタイプ | コンセプトの理解と試作品へのフィードバック | 最初の印象は？ どんな場面で使えそう？ 一番魅力的な点と不安な点は？ |
| MVP | 実際に使った反応を確かめる | 一番良かった点は？ ストレスや不便は？ このMVPがなくなったらどんな影響がある？ 使い続ける理由・やめる理由は？ |
| ベータ版・リリース直前 | 定量と定性を組み合わせる | 操作性は5段階で何点？ おすすめ度（NPS、0〜10）は？ どの画面で迷った？ |
| 運用・グロース | 継続理由と離脱理由、改善アイデア | 使い続けている理由は？ やめようと思ったことは？ 他社製品との使い分けは？ よく使う機能・使わない機能は？ |

<Note title="目安">プロトタイプは使い方を説明せずに触ってもらい、「最初にどこに注目したか」「どこで迷ったか」を聞く。顕在ニーズと潜在ニーズを見極めるには、深掘りを繰り返し、意見ではなく行動を聞き、理想と現実のギャップを質問する。</Note>
