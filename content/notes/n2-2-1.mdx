## 原則

- ロードマップは大枠の方向性を示すもの。大きな流れを描いて、小さく見ていく。
- 前提として、目的の設計が必要。ビジョンと目標が明確でないと、何を落とし込むかが定まらない。
- 一度作って終わりではない。定期的に更新する「生きたドキュメント」として扱う。

## ロードマップがもたらすもの

| 目的 | 内容 |
| --- | --- |
| ビジョン・方向性の共有 | 将来のゴールイメージを示す。共有できていないと、バラバラな方向に進む |
| 優先順位の明確化 | 「いつ」「どの領域に」「どれだけ労力をかけるか」を整理し、意思決定しやすくする |
| コミュニケーションの円滑化 | 何を、いつまでに、誰が、どう進めるかが整理され、ビジョンに照らして議論できる |
| 進捗管理とリスク対策 | マイルストーンを基準に進捗を測り、遅れや障害を早く見つける |
| 組織の一体感 | 中長期では、カルチャーやブランドイメージを反映することで一体感が生まれる |

認識のズレ、各役割、達成すべき課題が明確になることで、開発メンバーのモチベーションが高まり、チームの団結力や実行力も加速する。

## ロードマップの種類

| 種類 | 整理するもの |
| --- | --- |
| プロダクト開発 | 機能追加のタイミング、提供予定のバージョン、リリース予定日、各機能の優先度 |
| テクノロジー | 先端技術を活用したイノベーションの方向性、研究開発や技術導入のタイミング |
| サービス拡充 | 新しいメニューの追加、UIの刷新、新規顧客層への展開時期 |
| 組織・人材育成 | ビジョン実現に必要な人材スキル、採用計画、研修計画 |

## ロードマップと開発スケジュール

どちらも「目標までの計画表」だが、違いは粒度。

| | ロードマップ | 開発スケジュール |
| --- | --- | --- |
| 示すもの | 目標達成までの手段や施策を時系列で示した、大まかな実行計画 | プロジェクト完了までのタスクを事細かく書き出した、詳細な実行計画 |
| 単位 | 目的と目標（マイルストーン） | 直近の目標に至るタスク |
| 主に見る側 | Biz側 | Dev側 |

<Figure src="/figures/n2-2-1-2590.webp" alt="ロードマップと開発スケジュールの関係。現状から目的までの道筋に、ひし形の目標（マイルストーン）を置いたものがロードマップ。その下に、直近の目標までのタスクを細かく並べたものが開発スケジュール" caption="ロードマップは目標までの道筋、開発スケジュールは直近のタスク" />

<Caution>ロードマップにタスクまで描き込むと、全体像が掴みにくくなり、ドキュメントが膨大で更新も大変になる。詳細なタスクはプロジェクト管理ツールに任せ、ロードマップは俯瞰できるレイヤーに留める。</Caution>

<Figure src="/figures/n2-2-1-2592.webp" alt="細かすぎるロードマップの悪い例。タスクまで描き込まれ、全体像が掴みにくくなっている。大きな流れを描いて、小さく見ていくのがよい" caption="細かすぎると、全体像が掴みにくくなる" />

たとえば直近の開発スケジュールで要員確保が厳しい期間が見つかったら、ロードマップに立ち返り、その期間のタスクの入れ替えを検討する。全体の流れを見ながら、手前を細かく調整する使い分けになる。

<Figure src="/figures/n2-2-1-2593.webp" alt="ロードマップの作成と役割。PMが現状から目的までの目標をつないだ道筋を示す。開発側から「要員確保が厳しそうな期間がある」と相談されたら、ロードマップに立ち返って「ではその期間のタスクの入れ替えを検討しよう」と判断する" caption="ロードマップに立ち返って、手前の調整を判断する" />

## 作る前にそろえておくもの

| 前提条件 | 内容 |
| --- | --- |
| 明確に定義されたゴール | 「私たちは何を達成したいのか」。「利用者の声を集めたい」だけでは曖昧なままになる |
| 制約条件とリソース | 予算、人員、外注や協力企業との契約条件、スケジュールの制限。人員のスキル、ツールの有無、費用。今後必要になるリソースや潜在的な制約も挙げておく |
| 関係者の合意 | 計画段階から巻き込む。合意のないロードマップは実行段階で抵抗や混乱を生む |
| 想定リスクと対応策 | あらかじめリスクを想定し、表面化したときの行動を決めておく |
