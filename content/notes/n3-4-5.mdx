## 原則

- 聞く8割・話す2割。ユーザーヒアリングの成功確率は、相手の発言量に比例する。
- 課題特定のためには、1対1のインタビューが最も効果的。短い期間に複数人に聞く。
- 優れたPMは、定期的に自らユーザーに会っている。すべての答えはユーザーが持っている。

## ユーザーヒアリングとは

ユーザーの現状や悩み、期待、行動などを幅広く理解するための情報収集。数値化できない情報を分析し、仮説の構築と検証をする定性調査で、「体験を深掘りする質問」ができることが強み。

| 目的 | 内容 | ゴール |
| --- | --- | --- |
| ファクト集め | 自分に足りない情報を補う。ドメイン知識がない、新任でプロダクト理解がない、新しい機能を作るときに必要 | 「ユーザー」「課題」「解決策」の仮説が持てること |
| 仮説検証 | 確かめたいことを検証する。誰が最も大きな課題を持っているか、どんな課題か、どんな解決策なら解決できるか | ただの仮説を「確からしい仮説」にすること |

<Note title="目安">人数は5〜10人がおすすめ。toBはユーザーヒアリング主体、ヒアリングが難しいこともあるtoCはデータ分析主体で組み合わせる。</Note>

### 手法

| 手法 | メリット | デメリット |
| --- | --- | --- |
| デプスインタビュー（1対1） | じっくり話が聞ける。30分〜1時間で実施でき、回数を増やしやすい | 経験とスキルが必要。候補者選びにも一定の時間がかかる |
| グループインタビュー（1対複数） | 複数人からまとめて話が聞ける | 他の人の意見に影響され、検証しにくい。回数を重ねにくい |
| エスノグラフィ（行動の観察） | 言葉にできない原因に気づける、他にない質の高い情報が得られる | 時間が相当かかる。解釈に経験とスキルが必要 |

## 心得

| 項目 | 内容 |
| --- | --- |
| 探偵になったつもりで臨む | 犯人（本当の課題）を見つけるためにファクトを集めて仮説を作る。犯人を決めつけない |
| 調べられる情報は事前にリサーチする | 聞かなくても分かる情報は調べておくのがマナー（確認で聞くのはOK） |
| 質問項目を頭に入れる | 丸暗記でなくても流れは把握し、時間を最大限有意義にする |
| 感謝を伝え関係性を築く | 忙しい中で協力してもらっている。次回以降も協力してもらえる関係を作る |
| 必ず議事録を取る（できる範囲で録画する） | チームに共有するまでがPMの仕事。言葉にして残すと、チーム全体の解像度が上がる |
| どんな返答も否定せず受け止める | 望んだ回答が得られなくても否定せず、別の候補者を紹介してもらう |
| 聞く8割・話す2割 | とにかく話を聞いて深掘りする |

## 準備

- まず目的をはっきりさせる。どんな情報を得たら成功なのか（ゴールは<NoteLink id="n3-4-2">目標とゴール設定</NoteLink>）
- ドメイン知識がなければ、事前にリサーチして最低限の知識と自分なりの仮説を持つ。ドメイン知識があれば、誘導尋問にならないよう注意する。自分の知識が他の人の常識とは限らない
- 場所は静かで落ち着いた、適度にプライバシーが確保される環境にする。対面なら向かい合わせより斜めや横並びに座ると緊張がやわらぐ
- 録音や録画の有無と使い道を確認し、了承を得る。「個人が特定される形で外部に共有しない」「許可なく他の目的に使わない」と伝える
- オンラインでは、通信環境と接続方法の共有、顔が明るく映る照明、相手が映る画面の近くにカメラを置く、音声のズレを見越したリアクションを意識する

## プロセス：ヒアリングの進め方

<Steps>
  <Step title="アイスブレイク">天気や雑談で緊張をほぐす。目安は2〜3分で、長引かせない</Step>
  <Step title="目的を共有する">「今日は○○について正直な意見を伺いたい」と方向性を伝える</Step>
  <Step title="メインの質問と深掘り">用意した大きな質問から、プロービングで背景や理由を引き出す</Step>
  <Step title="まとめと確認">「私が理解した内容は○○で間違いありませんか？」と要約して確かめる</Step>
  <Step title="クロージング">感謝と今後の流れを伝える</Step>
</Steps>

## ラポール

相手との間に築かれた信頼関係、心が通じ合った状態。インタビューの根幹で、本音を話しやすくし、対話をスムーズにし、長期的な信頼関係の土台になる。傾聴と共感が、ラポールを築く2大エンジン。

| 項目 | 内容 |
| --- | --- |
| 寄り添う姿勢 | 相手を知ろうとする気持ちを表す、立場を尊重する、先入観を持たない、安心感を提供する |
| 傾聴 | 相づち・うなずき、オウム返し、要約と確認。「先ほどおっしゃった○○は、こういう意味ですか？」 |
| 心理的安全性 | 「ここで話しても否定されない」と感じてもらう。適度な自己開示は距離を縮めるが、あくまでスパイス程度 |
| 非言語 | アイコンタクト、姿勢・ジェスチャー、声のトーン・テンポ。低く落ち着いた声でゆっくり話す |
| スタイルを合わせる | 話のペース、専門用語のレベル、相手の文化や価値観に合わせる |

### 共感と同調は違う

共感は相手の感情に寄り添い、理解を示すこと。同調は「自分も全く同じだ」と受け入れてしまうこと。相手の視点に立ち、その思いを一度受け止める。

<Cards cols={2}>
  <Card label="感情ラベリング">「色々試したけど改善されず、焦りや不満を感じている状態なんですね」と感情に名前を付ける。断定せず「…と感じているようにも聞こえますが、いかがでしょう？」と提案的に</Card>
  <Card label="沈黙の活用">一瞬の沈黙は考えを整理する時間になる。長すぎると不安にさせるので「焦らず大丈夫ですよ」と声をかける</Card>
</Cards>

| 良い例 | 悪い例 |
| --- | --- |
| 「画面が複雑で操作に戸惑うことが多いわけですね。具体的にはどの画面で迷いますか？」 | 「そうですかね？慣れればそんなに難しくないと思うんですが」（感覚を否定している） |

## プロービング

回答者の背景や本音、潜在ニーズを引き出すために、より深く問いかけること。回答を明確にして誤解を防ぎ、潜在ニーズや痛みを引き出し、文脈を理解し、信頼関係を深める。

### タイミング

<Cards cols={2}>
  <Card label="回答が曖昧・抽象的なとき">「なんとなく」「とにかく嫌」はユーザーも具体化できていないサイン</Card>
  <Card label="回答に違和感を覚えたとき">「先ほどは○○とおっしゃいましたが、この違いはどこから来ているのでしょう？」と優しく聞く</Card>
  <Card label="背景をさらに深く知りたいとき">「具体的にはどんなシーンで便利と感じますか？」</Card>
  <Card label="会話が途切れそうなとき">「他に似たような経験はありますか？」</Card>
</Cards>

### 手法

| 手法 | やり方 |
| --- | --- |
| 言い換え | 「なるほど、あまり必要性を感じなくなった、ということですね？」 |
| 部分的な繰り返し | 「『○○が不便』とおっしゃいましたが、もう少し詳しく教えていただけますか？」 |
| 例示要求・具体化 | 「例えば、そのときどんな操作をしましたか？」 |
| 時系列アプローチ | 「最初に不満を感じたのはいつ？」「きっかけは？」「その後どう対処した？」 |
| 5Whys | 「なぜ」を繰り返す。しつこくならないよう言い回しを工夫する |
| 非言語の観察 | 「今、少し考え込まれていましたが、何か思うところがありましたか？」 |
| 沈黙 | すぐ次の質問をせず間をとると、自発的に話してくれる |
| 選択肢の提示 | 「面倒というのは、起動時間ですか？ログインですか？」 |

<Caution>質問攻めにしない。ユーザーのペースを尊重し、先回りして答えを補完しない。「それは本当に不便ですか？」のような価値観の押しつけや、「それは良いですね」のような評価的なリアクションを避ける。プライバシーや感情に関わる質問は、意図を伝えて了承を得てから。</Caution>

## よくある失敗

| 失敗 | 対策 |
| --- | --- |
| 聞く相手が不適切だった | 誰に聞くかは目的で決まる。分からなければ、最も使ってくれるユーザーの特徴から仮説を立てる |
| ヒアリングしたが次に何をすればいいか分からない | 実施前に目的、ゴール（ファクト集めか仮説検証か）、質問項目を用意する |
| 議事録がファクトと推測でごちゃごちゃ | 議事録は「ファクト」と「仮説検証」を分けて書く |
| ファクトと相手の憶測の区別がつかない | ファクトは「過去・現在のこと」、主観は「まだ起きていないこと」 |
| 何を質問したら良いか分からない | 目的設定から始め、質問内容はゴールから逆算する |
| 自分の話を優先してしまう | 「ここまでで私の理解に間違いがあったら教えてください」と確認を促す |
| 相づちばかりで深掘りできない | 「具体的にはどういうことが起きているんですか？」と追加で聞く |
| 結論を急ぐ | 「まだ隠れている問題はないか」を意識し、話しきってもらう |
| 雑談で終わる | リラックスしすぎず、時間配分と軌道修正を意識する |

## ヒアリングの後

<Steps>
  <Step title="議事録を整理・共有する">後から読んでも分かる内容にしてチームで共有する</Step>
  <Step title="ユーザーへフォローする">お礼を伝え、継続してヒアリングできる体制を作る</Step>
  <Step title="結果を分析する">実施前のイメージとどれくらいずれていたかを確かめる</Step>
  <Step title="フィードバックを集める">ステークホルダーや開発チームの意見で分析を深める</Step>
  <Step title="改善方針を決める">課題をより解決する機能やサポートに落とし込む</Step>
</Steps>

<Note title="補足">ヒアリング結果はただのファクトにすぎない。ここからどう分析するかでプロダクト開発の個性が出る。ユーザーの環境は常に変わるので、定期的なヒアリングをスケジュールしておく。</Note>
