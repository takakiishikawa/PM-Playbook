## 原則

- スクラムは「うまくいく方法」ではない。導入すれば60点は簡単に取れるが、80〜90点にするのが難しいフレームワーク。
- 開発がうまくいっても、プロダクトがうまくいかないケースが多い。プロダクトマネジメントなしの開発では、ムダなものを効率よく開発してしまう。
- スクラムの理論や価値基準は教条的だが、必ず役に立つ。定期的に読み返す。

## スクラムの理論

スクラムは、経験主義（知識は経験から生まれ、意思決定は観察に基づく）とリーン思考（ムダを省き、本質に集中する）に基づく。

| 三本柱 | 内容 |
| --- | --- |
| 透明性 | 成果物は見える必要がある。見えないと価値が下がり、誤解やムダを招く |
| 検査 | 頻繁で熱心な検査で、ゴールへの進捗や望ましくない変化・問題を検知する |
| 適応 | 検査で学んだことを適応し、ゴールと現状のズレを調整する。成果物だけでなくプロセス全体に及ぶ |

5つの価値基準は、確約（ゴールを達成し、互いに支える）、集中（スプリントの作業に集中する）、公開（作業や課題を公開する）、尊敬（能力ある独立した個人として互いを尊重する）、勇気（正しいことをし、困難な問題に取り組む）。

## 3つの役割

スクラムチームは職能横断型の専門家が集まった、通常10人以下の小さなチーム。プロダクトに必要なすべての活動に責任を持つ。

| 役割 | 責任 | 担い手の例 |
| --- | --- | --- |
| プロダクトオーナー（PO） | プロダクトの価値を最大化する結果に責任を持つ。仕事に優先順位をつけ、ビジネス価値と労力を見積もって意思決定する。作業は委任できるが最終責任はPO。組織全体でPOの決定を尊重する | プロダクトマネージャー |
| 開発者 | 作成物に責任を持つ。見積もって計画しコミットする。専門家として品質を作り込み、毎日計画を適応させる | エンジニア、デザイナー、QA |
| スクラムマスター | スクラムを確立させ結果を出すことに責任を持つ。コーチングし、障害物を取り除き、すべてのイベントを成立させる | プロジェクトマネージャー |

## 5つのイベント

| イベント | 内容 |
| --- | --- |
| スプリント | 1カ月以内の決まった長さの活動サイクル。スクラムの心臓の鼓動。短いほど予測しやすく、学習サイクルが短く、リスクも小さい。長さは見通し、システムや環境、チームの練度で決める |
| スプリントプランニング | スプリントの起点。POが価値向上の方法を提案し、開発者が話し合ってスプリントバックログを選び、作業に計画する |
| デイリースクラム | 毎日同じ時間・同じ場所で行う開発者のための計画イベント。進捗会議ではなく再計画の場 |
| スプリントレビュー | 成果をステークホルダーに示し、プロダクトゴールへの進捗を話し合うワーキングセッション |
| レトロスペクティブ | 個人、相互作用、プロセス、ツールなどをチームで検査する「ふりかえり」。改善案は次のスプリントバックログに入れてもよい |

## 3つの作成物

| 作成物 | 内容 |
| --- | --- |
| プロダクトバックログ | 価値の大きさで優先順位をつけた作業の一覧で、唯一の情報源。実現するとプロダクトゴールが達成される。優先度が高いものほど解像度が高い。長期の計画にロードマップを併用するチームもある |
| スプリントバックログ | プロダクトバックログから選んだ、そのスプリントで完了させる最優先の作業。開発者による開発者のための計画 |
| インクリメント | スプリントで完成した、届けられる状態の成果物。稼働テストもスプリント内で行う |

スプリントゴールはスプリント唯一の目的で、開発者が確約する。ゴールに影響が出ないよう、スコープを調整する。

<Caution>スプリントプランニングの前に、プロダクトバックログを準備しておく。開発・テストができ、見積もりができていて、完成の定義・受け入れ条件が決まっていること。準備を怠るとスクラムは回らない。</Caution>

## うまくいかない理由

- スクラムチームを作る必要がある
- スクラムイベントには時間がかかる
- 「やること」の準備にも時間がかかる
