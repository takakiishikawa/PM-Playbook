## 原則

- <Mark>**バックログは雑な機能アイデアの墓場になりがち。運用ルールを決め、開発チーム全員で認識をそろえる。**</Mark>
- 機能だけでなく課題を書く。課題の説明がないと、どんな機能が必要か判断できない。
- 継続的に手入れ（リファインメント）し、プロダクトの方向性とバックログの内容を常に一致させる。

## バックログがもたらすもの

新しいアイデアや要求、直すべきバグなど、あらゆる「これからやるべきこと」を一覧にし、優先度や難易度を添えたもの。開発の透明性が上がり、優先度が明確になり、リソース計画やスプリント計画が立てやすくなる。

## 3種類のバックログ

| 種類 | 内容 |
| --- | --- |
| プロダクト・バックログ | 今後のリリースで取り組むべき機能と優先順位。アイテム、説明、ステータス、エピック・テーマを整理する |
| リリース・バックログ | プロダクト・バックログから、リリースごとに機能とタイミングを整理したもの。主にウォーターフォールの大規模開発で使う。アジャイルではスプリント・バックログで代用することも多い |
| スプリント・バックログ | スプリント期間ごとに何を開発するかを、タスク・見積もり時間・担当者まで分解したもの |

## 階層構造

| 単位 | 内容 |
| --- | --- |
| エピック | 大きな要件や機能群をまとめた単位。複数のスプリントやチームにまたがることも多い |
| ユーザーストーリー | エピックを細分化した単位。ユーザーのニーズを端的に表す |
| タスク・サブタスク | 開発メンバーが日々取り組む具体的な単位 |

バックログには機能開発だけでなく、バグ修正、テクニカルデット（技術的負債）の返済、リファクタリングも入れる。バグはユーザーストーリーと同等に優先度をつけて管理する。テクニカルデットも長く放置すると品質や開発効率が落ちるので、継続的に優先順位を検討する。

## 誰が関わるか

| 役割 | 担うこと |
| --- | --- |
| プロダクトオーナー／PM | 全体を管理し、ビジネス的価値を重視して優先順位を決める |
| 開発チーム | 技術的な妥当性を確かめて見積もり、ストーリーを細分化する |
| ステークホルダー | 要望や期待を伝え、できた機能にフィードバックする |

## リファインメント

バックログの手入れのこと。グルーミングとも呼ぶ。スクラムでは定期的に時間を設け、項目の内容・優先度・見積もりを見直す。

1. チケットの優先順位を入れ替える
2. 抽象的なユーザーストーリーを具体的にする
3. 重複するチケットをまとめる
4. 起案者にチケットの詳細をヒアリングする
5. 関連性の高いチケットをグループ化する
6. 工数の大きいチケットを分割する

バグ修正が急務になった、先に公開すればシェアを取れる、競合が先行する分野に対抗する必要が出た、といった変化をタイムリーに反映する。実装済みの機能と重複するもの、方針転換で不要になったもの、別のストーリーに吸収されたものはクローズかアーカイブする。

## 運用のルール

| ルール | 内容 |
| --- | --- |
| チケット化する人を限定する | 誰でも作れると管理しにくい。アイデアや要望は別ドキュメントで整理し、チケットは主にPMが作る |
| 更新のタイミングを決める | 毎週の会議など、時間を決めておくと最新に保ちやすい |
| 変更があれば随時更新する | エンジニアやデザイナーとの会話で変わったことは忘れずに書く |
| 開発チーム全員で振り返る | チケットの内容の認識合わせをする |
| 思いつきはチケット化しない | 全部をチケットにすると混乱する。検討のうえ大事なものを残す |
| 古いチケットはアーカイブする | やらないと決めたチケットは非表示にする |
