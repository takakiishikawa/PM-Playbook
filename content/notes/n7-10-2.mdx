## 原則

- <Mark>**PMが考えていることは思っている以上に伝わっていない。この前提でコミュニケーションを密にする。**</Mark>
- PMは1人では開発できない。一緒にいる仲間を知ることから、優れたプロダクト開発は始まる。
- 知ったかぶりはせず、相手の専門スキルと知識を活かしてプロダクトを良くする。

## PMに期待されていること

| 相手 | 期待 |
| --- | --- |
| 共通 | ベストなタイミングで必要な情報や資源を用意し、手を止まらせない。ビジネスやユーザーの課題を解像度高く伝える |
| デザイナー | 感覚ではなく、ビジネスやユーザーの目線で判断する |
| エンジニア | 期間・依存関係・クリティカルパスを理解して依頼する。技術用語を理解して歩み寄る。プロジェクトを俯瞰して合理的に判断する |

## 気をつけること

| ポイント | 内容 |
| --- | --- |
| 思考過程を共有する | ヒアリングの結果、課題の特定、解決策の検討を共有し、「なぜ」を理解してもらう |
| 悩んだらすぐ相談する | 15分くらい悩んだら相談したほうが早い。頼られる側も嬉しい。テキストでぼやくだけでもよい |
| 積極的にフィードバックをもらう | エンジニアやデザイナーから積極的に意見をもらう |
| 相手のスキルレベルを考える | スキルレベルによって話せる内容が変わる。開発ができなくても、メンバーの強み・弱みは把握しておく |
| 最低限の技術知識を持つ | 技術とデザインの基礎知識、時流のキャッチアップ |

## 相手を知る

| 相手 | 特徴 | 協働のコツ |
| --- | --- | --- |
| エンジニア | 技術が好き。口頭説明が苦手な人が多く、エンジニア同士の会話を好む | 作る機能は理由と一緒に説明する。きれいなコードに固執せず、開発スピードも重視する |
| デザイナー | デザインが好き。口頭説明が苦手な人が多く、ユーザー体験を考えるのが得意 | モダンなデザインと同時にUXを重視する。具体的な成果物と一緒に会話する |

開発者は、自分の仕事を理解していない相手とはコミュニケーションを取りたがらない傾向がある。PMが相手を理解して寄り添う。

## コンフリクトへの向き合い方

| アプローチ | よくある場面 | 効果的な関わり方 |
| --- | --- | --- |
| 直面・問題解決 | エンジニアとデザイナーが実装方法で対立している | 双方の意図を確認し、ユーザー価値を基準に最適解を探す。技術的制約とUX要件の両立案を見つける |
| 鎮静・適応 | ステークホルダーが感情的で、建設的な議論ができない | まず懸念を傾聴し共感を示す。クールダウンの時間を置き、データを整理してから改めて議論する |
| 協力 | チーム間の連携不足でリリースが遅れそう | 各チームの状況を可視化し、共通ゴールを再確認する。定期的な同期の場でブロッカーを早く解消する |
| 強制 | セキュリティ問題が発覚し、即座の対応が要る | 優先順位を明確に伝え、他のタスクを止める判断を下す。理由を簡潔に説明し、リソースを確保する |
| 妥協 | スコープと納期の両方を求められ、どちらも譲れない | MVPの範囲を定義してフェーズを分け、重要な機能を先に、残りは次のフェーズで対応する合意を取る |
| 撤回・回避 | 小さな仕様の違いで議論が長引いている | ユーザーへの影響が小さければ「まず実装して検証する」と判断する。ABテストや後から変えられる設計で進める |

## 伝え方

| 方法 | 使い方 |
| --- | --- |
| ドキュメント | 伝えたいことの土台。全員と常に同期するのは無理なので、ドキュメントの力を借りる |
| 会議 | 必要に応じて行う。同期のための会議を増やしてリソースを圧迫しない |
| チャット | こまめな共有と相談 |

<Caution>会議だけに頼って、口頭で伝えたつもりになるのは危険。ドキュメントにしつつ、会議とチャットで伝える。</Caution>

相談する前に、①目的・伝えたいこと、②現状の課題・相談したいこと、③ネクストアクション、の3つを整理する。言語化のスキルは、ドキュメントを1つずつ作る習慣を繰り返すことでしか上がらない。
