## 原則

- PMは「チケットの番人」。責任をもってチケットを管理し、課題を解決できるかを判断する。
- チケットには課題・機能など必要な情報がすべてあり、常に最新になっていることが大事。更新のタイミングはチーム内で決めておく。
- チケットを作るだけではまだ半分。開発にどう活かすかまでがPMの役割。

## なぜチケットを作るのか

ソフトウェア開発ではほぼ100%作るもので、カンバンボードやバックログで管理する。アジャイル開発ではすべての開発の元になり、ウォーターフォールでも機能ごとの要件はチケットで管理することが多い。

課題だけ理解しても、どんな機能があれば解決できるかは分からない。たとえば「ユーザーにもっと講義を観てほしい」なら、自動再生、進捗表示、動画レコメンドなど複数考えられる。**どんな機能があれば課題が解決するかを企画してチケットにすることで、エンジニアやデザイナーに理解してもらえる。**

チケットがないと、どんな開発をすべきか分からず、課題を解決できるかも判断できず、スケジュール管理もできず、ビジネスKPIへの影響も分からない。

## 良いチケットの3要素

1. 誰が読んでも分かりやすい。開発チームだけでなく、他部署の人や上司が読んでも分かる
2. 解決するべき課題が理解できる。機能だけでなく課題の詳細を伝える
3. 具体的な機能と達成基準がある。どんな機能で、どういう状態を目指すのか

## 書く項目

| 項目 | 書くこと | 例 |
| --- | --- | --- |
| チケット名 | 簡潔に。後から探しやすいよう検索キーワードを含める | レッスン進行状況の可視化 |
| 概要サマリー | 目的と背景を100〜200文字で | 学習進行状況を一覧で確認する手段がないため、機能を追加して学習効率とモチベーションの向上を図る |
| 起きている課題 | 課題の詳細。残しておくと、より良い機能を思いつくことも多い | 何をどれだけ学習し、何が残っているかが分からず、継続しにくいという回答がアンケートで10件あった |
| 作る機能とユーザーストーリー | 機能と、ユーザーがそれをどう使って課題を解決するか | ダッシュボードで進行状況と残りのレッスンが分かり、そこから講義へ直接遷移できる。今後追加されるコンテンツも分かる |
| 達成基準（受け入れ基準） | どんな状態ならリリースできるか | 進行状況バーが表示される／レッスン完了のたびにリアルタイムで更新される／適切にテストされ新たなバグがない |

チケットの項目は組織によって差があるが、大事な原理原則は変わらない。

## チケットの活かし方

| 活かし方 | 内容 |
| --- | --- |
| 機能アイデアはチームで議論する | 有効な機能を決めつけず、チームでアイデアを持ち寄る |
| できるだけ小さい単位で作る | 大きすぎるチケットは具体的な行動に落とせず意味がなくなる |
| 課題のファクトを添える | 機能と課題をセットにすると、後からより良い機能を思いつくこともある |
| 開発チームと毎週認識をそろえる | 作って終わりではなく、認識をそろえるまでが仕事 |
| 達成基準はチームで議論する | 工数や技術的な都合でやれることは変わる。レビューをもらって進める |
| やらない機能を決める | やる機能と同じくやらない機能を決めないと、認識がそろわず素早くリリースできない |
| 古いチケットは更新・アーカイブする | 古いアイデアや、やらないと決めた機能を放置しない |
