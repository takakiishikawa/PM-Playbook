## 原則

- ユーザーストーリーは「誰が」「何のために」「何をしてほしいのか」を明確にする。
- すべてが優先度「高」では意味がない。課題解決に役立ち、確信がある機能から優先する。
- 必要な情報はプロダクトの業界や種類で異なる。必要な項目を判断し、チケットを最適化するのがPMの仕事。

## ユーザーストーリーの書き方

「As a［ユーザーの種類］, I want to［したいこと］, So that［理由］」の形で書く。

| 良い例 | 悪い例 |
| --- | --- |
| 購入者として、購入履歴ページにレビュー機能を追加してほしい。以前に購入した商品の評価を共有したいから | 購入者として新機能を追加してほしい |

## チケットに書く項目

| 項目 | ポイント |
| --- | --- |
| カテゴリ | 新機能開発、機能改善、不具合修正、保守・運用、アイデアなどで分けると整理しやすい |
| 担当者・起案者 | 忘れがち。誰が作ったか記録しないと、検討時に確認する手間がかかる |
| チケット名 | 主語や目的をタイトルに含める |
| ユーザーストーリー | 目的と、ユーザーにどうなってほしいかを分かりやすく伝える |
| 優先順位 | 課題解決に役立ち、確信がある機能から |
| 受け入れ基準 | どうなればリリースしてよいか |

その他の情報（開発工数の見積もり、リリーススケジュール、スプリント計画など）は開発チームで議論して決める。

| チケット名の良い例 | 悪い例 |
| --- | --- |
| ユーザープロフィールページで写真をアップロードできるようにする | プロフィールを改善する |
| チェックアウト時のクレジットカード検証エラーメッセージを明確にする | エラーメッセージを修正する |
| ログイン後のリダイレクト時間を最適化する | パフォーマンスを上げる |

<Note title="例：ダッシュボードのUI改善">ストーリーは「ダッシュボードのUIが直感的になり、自分の進捗や必要な情報を簡単に見つけられ、学習を続けやすくなる」。要件はレイアウトと色の見直し、重要な情報が目立つ配置、ユーザビリティテストでの改善点の抽出。優先順位は高、見積もりは3ストーリーポイント。受け入れ基準は、新デザインが全ユーザーに適用される、テスト参加者の80%以上が以前より使いやすいと感じる、サポートへの関連問い合わせが20%減る。</Note>

## 優先度のつけ方

ユーザー価値、ビジネスインパクト、緊急度、作業量・実装の難しさの4つを基準に、ユーザーストーリーやバグ、タスクに優先度をつける。その前提として、「誰の、どんな課題を解決するか」を明確にしておく。

- **ペルソナを置く**：代表的なユーザー像の行動パターンやニーズを考える。
- **顧客価値を明確にする**：なぜその機能が必要か、ビジネス的なインパクトはどうか。
- **技術的に検討する**：開発チームと技術的な制約や実装可能性を確かめる。
