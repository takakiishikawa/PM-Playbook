## 原則

- PRD（Product Requirement Document／要求仕様書）を作る目的は、なぜその機能開発が必要なのかを誰が見ても分かるようにすること。
- PMが主に考えるのは「要求」。要件はエンジニアと一緒に考えればよい。
- 言語化できないものはチームで議論できない。「言語化できるまで考える」ことがPMの大事な仕事で、その代表例がPRD。

## 要求と要件

| | 要求（Requirements） | 要件（Specification） |
| --- | --- | --- |
| 中身 | 具体的な機能ではなく、主に「課題」。課題を解決したい気持ち | 要求を満たすための機能を技術的に具体化したもの |
| 含むもの | ニーズ、ユーザーからの要望、ステークホルダーからの要望、ビジネス上の目標 | 開発言語、インフラ設計、技術的な制約、API |
| 例 | ユーザーは簡単に写真を加工して友達と共有したい | カメラロールから写真を選び、コメントを追加して共有できる機能 |

## PRDを作るメリット

<Figure src="/figures/n4-2-5-1667.webp" alt="PRDがない場合とある場合の比較。PRDがないと、チームメンバー全員の質問がPMに集中し、PMが個別に回答する。PRDがあると、メンバーはPRDを見れば答えが分かり、PMへの質問が減る" caption="PRDがあれば、個別に答える代わりに「PRDを見て」で済む" />

| メリット | 内容 |
| --- | --- |
| コミュニケーションコストが下がる | PMが忙しくなる最大の理由はコミュニケーション量。個別に答える代わりに「PRDを見て」で済み、ドキュメントが代理でコミュニケーションしてくれる。意思決定を言語化すると、上司やステークホルダーへの説明も格段にしやすい |
| 開発効率が上がる | 開発が進むと疑問が生まれる。立ち返る場所がPRDになる。エンジニアやデザイナーが多いほど効く |
| 意思決定が知見になる | 意思決定はブラックボックスになりがち。新しいメンバーも過去の検討経緯を追える。なんとなくで判断しないために言語化する |

## PRDを管理する

PRDは作って終わりではない。管理・更新することがPMの大事な仕事。

| 項目 | 内容 |
| --- | --- |
| 具体的に分かりやすく書く | 主語や目的語が抜けると、後から読んで分からなくなる。専門用語はできるだけ使わない。言葉の定義を明確にする |
| バージョンを管理する | 特に大事な項目 |
| 定期的にレビュー・更新する | 実際のプロダクトとずれていたら直す。できるだけ毎日確認し、最低でも週1回は確認・更新する |
| 大きな変更点を随時共有する | 開発に影響する変更は、チームだけでなく上司・ステークホルダーにも共有する。ドキュメントはあるだけでは共有ではない。PMから定期的・積極的に投げかける |
| チームからフィードバックをもらう | PM1人で完璧なものは作れない。上司やステークホルダーとの認識のズレは後の炎上の原因になる。最初からPRDを見せて認識をそろえる |

| 書き方 | 悪い例 | 良い例 |
| --- | --- | --- |
| 主語と目的語を書く | 〇〇の機能をリリースする | 本番環境に〇〇の機能をリリースする |
| 専門用語を避ける | PMFをしたのでGTM戦略を実行する | 売上を作り、それを拡大させる |
| 言葉を定義する | できるだけ早くリリースする | 2週間以内に最小工数でリリースする |
