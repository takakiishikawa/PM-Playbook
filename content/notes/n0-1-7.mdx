## 原則

- <Mark>**自分の知識や経験も1つの進め方にすぎないと割り切る。特に「課題の決めつけ」は危険。**</Mark>
- 「もしかしたら他の課題があるかもしれない」という健全な自己否定が大事。
- PMで大事なのは「誰の・どんな課題を解決するか」。自分の経験ではなく、ユーザーに向き合う。

## ドメインエキスパートとは

特定の業界・業種（ドメイン）で専門的な知識・スキル・経験を持つ人。特にToB SaaSなど法人向けプロダクトで求められる。業界ごとに特殊な商習慣や不文律があるとき、経験が活きる。金融、労務・人事、医療、エネルギー、製薬、自動車、建設、通信、AIなど。ドメイン知識がないPMは、それ専用の学習が必要になる。

## 強み

| 強み | 内容 |
| --- | --- |
| 課題の解像度が高い | 専門性が求められる業界ほど、課題の理解そのものに時間がかかる |
| 具体的な改善企画を考えやすい | 最初から具体的な機能や改善プロセスを考えられる |
| 業界の不文律に対応できる | 明文化されていない商習慣やルールにも適応しやすい |
| 業界トレンドを理解している | 一般には知られていない動きが開発に役立つ |
| 仲間から信頼されやすい | 開発メンバーだけでなく、セールスなどからも頼られる |

## 弱み

| 弱み | 内容 |
| --- | --- |
| プロダクト開発の理解不足 | 技術・デザインはまったく異なる専門知識 |
| ビジネス経験不足 | プロダクトがどうユーザーに届けられるかイメージしにくい |
| 自分の経験に固執しやすい | 他の人の意見や進め方を取り入れる柔軟性を失いやすい |
| 課題を決めつけやすい | 自分が持っている課題がすべてだと思い、他の課題に気づきにくい |

「自分はこうやっていた」が、他のユーザーにも最適とは限らない。これまでの仕事のやり方を否定することも多い。新しい学習とアンラーニングを繰り返す姿勢と好奇心を持つ。

## するべきこと

1. 専門知識を維持し、最新の情報でアップデートする
2. 定期的にユーザーヒアリングをして、課題の現場を知る
3. 専門知識を仲間に伝え、仕事を進めやすくする
4. プログラムとデザインを作ってみて、プロダクト開発の経験を積む
5. セールスやCSの商談に同席し、プロダクトがどう届くかを知る

ドメイン知識にPMスキルを掛け算できると、その業界で圧倒的な強みになる。
