## 原則

- <Mark>**ユーザーの声をそのまま受け取らず、背景を探る。「この機能が欲しい」が真の解決策とは限らない。**</Mark>
- 分類は整理の手段であって目的ではない。細かくしすぎると、要求本来の意味がぼやける。
- 開発者目線で語らない。技術的な興味や実装しやすさより、ユーザーが求める価値を優先する。

## ユーザー要求とは

ユーザーが課題を解決したり目的を達成したりするために必要だと考える要望やニーズ。広く捉えれば、期待や希望、潜在的に感じている問題点を含めた「解決してほしい事柄」。

| 種類 | 内容 | 例：PCを買い替えたいユーザー |
| --- | --- | --- |
| 顕在要求 | ユーザー自身が自覚し、言葉になっている | 処理速度が速く、画面が大きいPCが欲しい |
| 潜在要求 | 自覚していない、言語化されていない | 実はゲーム配信をしたいがスペック不足で諦めていた。目の疲れを減らすディスプレイが欲しい |

<Caution>初期に要求の定義を誤ると、機能や仕様がユーザーの求めるものから外れる。「手軽に写真が撮れるアプリが欲しい」のに、開発側が高機能な画像編集ばかりに注力する、といったズレは「こんな機能があったら喜ぶだろう」と勝手に想像することで生じる。</Caution>

## 要求を分類する

分類すると、優先順位をつけやすくなり、チームの役割分担が明確になり、UI・UXやセキュリティなどの考慮漏れが減る。

| 軸 | 内容 |
| --- | --- |
| 機能要求 | ユーザーが行いたい操作や、システムが提供すべき機能。例：商品を検索したい、複数の商品を一括で比較したい |
| 非機能要求 | パフォーマンス、セキュリティ、スケーラビリティ、ユーザビリティ、障害対応など品質や運用に関わるもの。例：同時アクセスでも遅くならない、カード情報を安全に管理する |
| 業務プロセス | 業務フローの順に並べる。例：営業なら顧客調査 → 商談 → 見積もり → 受注 → 納品 → 請求書発行 → アフターサポート |

### Kanoモデル

| 要件 | 内容 | 例 |
| --- | --- | --- |
| 必須要件 | 当たり前に備わっていてほしい。欠けると不満になる | 車の安全性、サイトのログイン |
| 期待要件 | あればあるほど満足し、なければ不満を感じる | 車の燃費、検索の速さ |
| 魅力要件 | あるとすごく嬉しいが、ないからといって不満にはならない | 自動駐車、AIによる商品レコメンド |

## 要求を引き出す方法

| 方法 | ポイント |
| --- | --- |
| インタビュー | 回答を誘導しない。オープンクエスチョンで本音を話してもらう |
| アンケート | 多数から定量データを集める。深い動機は引き出しにくいので、インタビューと組み合わせる |
| 観察調査 | 使い方や業務で手間取っている様子を直接見る。言語化されていない潜在要求の発見に有効 |
| ワークショップ | ユーザー・開発者・関係者が一緒に洗い出す。ステークホルダーが多いと合意形成を早められる |

## プロセス：ユーザー要求を整理する

<Steps>
  <Step title="洗い出す">できる限り多くの要求をリスト化する。重複や矛盾があってもよいので、声を余さず拾う</Step>
  <Step title="分類する">機能／非機能、Kanoモデル、業務プロセスなどの軸でグルーピングし、重複をまとめる</Step>
  <Step title="精査して優先度をつける">「ログイン機能」でもSNS連携や二段階認証など細分化される。ビジネス上のメリット、開発コスト、ユーザーへのインパクトから優先度をつける</Step>
  <Step title="要求定義書にまとめる">関係者が認識を共有する土台で、要件定義・設計・リリースまでの指針になる</Step>
  <Step title="レビューして合意する">ユーザーや関係者とレビューし、認識のズレを直してから次の工程に進む</Step>
</Steps>

要求を定義するとスコープが明確になる。曖昧だと後から仕様変更が頻発してプロジェクトが膨れ上がり、不十分だと必要な機能が抜け落ちる。技術的に難しい要求やコスト・納期に大きく響く要求は、早い段階でリスクとして共有する。要求は時代とともに変わるので、定期的に見直す。

## As-Is：現状を正確に把握する

現状をできるだけ客観的かつ正確に捉える。どこまで深く捉えられるかが、要件定義やギャップ分析の質を左右する。

| 要素 | 内容 |
| --- | --- |
| 業務プロセス | 業務フロー、入力・出力、担当者、利用しているシステム |
| 組織体制 | 役割分担、責任の所在、部門間の連携 |
| ツール・システム環境 | ソフトウェア、ハードウェア、クラウド、データベース |
| 課題や問題点 | 非効率、エラー、重複作業 |
| 運用ルール・ドキュメント | マニュアルやガイドラインの有無と、実際に守られているか |

| 把握方法 | ポイント |
| --- | --- |
| インタビュー | 業務手順、扱うツールや書類、困っている点を事前に整理して聞く。結果は文書化し、本人に確認してもらう |
| 現場観察 | 操作画面の遷移、書類の受け渡し、作業頻度やタイミングを見る。口頭では出てこない場当たり的な対応やムダが見つかる |
| 文書レビュー | 業務フロー図、申請書や報告書のフォーマット、規約を確認する。実際の運用と食い違っていないかも見る |

集めた情報を業務フローやシステム構成として図にする。部門間の連携、どのステップでどのツールを使うか、入力と出力は何かを描くと、「ここは誰が担当か」といった疑問が浮かび、正確な情報が集まる。見えてきた課題は、優先度や原因・背景を添えてリストにし、「なぜ起きているのか」で掘り下げる。

## To-Be：あるべき姿を描く

単なる理想論ではなく、実現可能で具体的な将来像。開発や導入の方針・スコープを決める青写真になる。

- 経営目標や事業戦略と一致しているか
- ユーザーのニーズや要望を満たせるか
- 技術的・人的リソースで実現可能か
- コストやスケジュールに無理がないか
- 運用・保守を含めて継続的に維持できるか

売上・利益率、市場シェア、顧客満足度、効率化・コスト削減、新規ビジネスモデルといった**経営視点の大枠の目標を理解していないと、部分最適なTo-Beになる**。一方でユーザーの要望を全部聞けばコストと期間が膨らみ、経営視点だけで機能を絞れば現場に使われない。両者の妥協点を探るのが上手なTo-Beのコツ。

## ギャップ分析

As-IsとTo-Beを並べ、業務フローや要件項目ごとに差分を挙げる。例：発注処理が現在は5ステップ、To-Beでは3ステップ。

- 見る差分：ステップ数・作業時間・担当者数、機能の有無、データの扱い方、自動化の割合
- 差分ごとに「なぜ差があるのか」「どうすれば埋められるか」のアクションを紐づける

ギャップ分析は、優先度の高い問題の明確化、段階的な対応策（ロードマップ）、必要なリソースの見積もり、合意形成の裏付け資料に使う。結果が曖昧だと、要件定義や実装でブレが生じ、スコープオーバーにつながる。
