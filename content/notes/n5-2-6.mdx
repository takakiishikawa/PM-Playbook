## 原則

- 技術スタックの選定は、ビジネス要件・ドメイン要件との整合が前提。
- どんなに優れた技術でも、チームが習熟していなければ開発効率も品質も下がる。
- リスク評価まで含めて選定として扱う。後になって想定外のコストや手戻りが起きる確率を下げる。

## 技術スタックとは

ソフトウェアを作るときに使うプログラミング言語、フレームワーク、ライブラリ、データベース、サーバー、クラウドインフラなどの総称。開発から運用までに必要な技術群。

## 選定が与える影響

| 影響 | 内容 |
| --- | --- |
| 開発効率・生産性 | チームの得意な技術に統一すれば生産性が上がる。慣れない技術は学習とトラブル対応で遅くなる |
| メンテナンス性・拡張性 | リリース後も進化し続ける前提で選ぶ。人の増減や技術刷新でボトルネックにならないか |
| 品質・パフォーマンス | 同じ機能でも処理速度やメモリ使用量に差が出る。高トラフィックなら性能要件を満たすものを選ぶ |
| コスト・ライセンス | オープンソースはライセンス料を削れるが、サポートやセキュリティ対策を自前で行うことが多い。商用はサポートが手厚いが、費用が収益を圧迫しうる |
| 採用・チームビルディング | その技術を扱える人材を確保する必要がある。採用しやすい技術か、ニッチでも付加価値が高い技術か |

## 考慮するポイント

| 項目 | 内容 |
| --- | --- |
| ビジネス・ドメイン要件 | 金融なら高いセキュリティと信頼性、医療や製造なら規制や標準規格。スタートアップ的に素早く立ち上げるなら、軽量なフレームワークやマネージドサービスで開発スピードを優先する |
| トレンドとコミュニティ | コミュニティが衰退すると、バグ修正やバージョンアップが遅れる。公式ドキュメント、企業のサポートプラン、LTS（長期サポート）の有無も確かめる |
| チームのスキルセット | 見落としがち。新技術への挑戦はモチベーションや差別化になるが、リリース時期、品質要件、教育コストを踏まえて習熟できるかを見極める |
| ビジネスサイドとの調整 | 学習コストでリリースが遅れるなら、MVPから徐々に広げられるか。クラウドは運用が楽な反面、規模が大きくなると月額が高額になる。予算との整合を確かめる |
| チーム内の合意 | エンジニアの挑戦したい気持ちと安定稼働のバランスを取る。コーディング規約やアーキテクチャ方針も同時にルール化する |

## プロセス：選定する

<Steps>
  <Step title="要件を洗い出す">ビジネス要件、機能要件、非機能要件（性能、セキュリティ、可用性、拡張性、運用・保守性、災害復旧）を整理し、KPIやSLOなどの数値に落とす。すべてはカバーできないので優先度をつける</Step>
  <Step title="候補を挙げて調べる">領域ごとに候補を挙げ、機能・拡張性、性能の実績、セキュリティ、ドキュメントやコミュニティ、ライセンスとコスト、学習・採用コストで整理する。可能なら小規模なPoCで使用感を確かめる</Step>
  <Step title="評価して決める">必須要件をYes/Noで判定し、重要な指標ごとにウェイトをつけて点数化する。メンバーやステークホルダーとレビューし、スコアの高いものを選んで経営陣に妥当性を説明する</Step>
</Steps>

## リスクへの備え

バージョンが若くバグが多い、近くメジャーアップデートで互換性がなくなる、特定ベンダーへの依存で値上げやサポート終了の影響を受ける、といったリスクを洗い出す。

- 代替技術の選択肢を確保する
- ベンダーとの契約を見直し、長期サポートやSLAを確保する
- バージョンアップ方針や移行コストを計画に織り込む
