## 原則

- ヒアリングレポートは「次のアクションにつなげるための指南書」。
- 最初に「誰に」「何を伝えたいか」を意識し、レポートのゴールを決める。
- 共有のプロセスを怠ると、ユーザーのニーズや課題が方針に反映されず、意思決定に活かされない。

レポートの目的は3つ。ユーザーの声から何を学びたいか、行動特性や課題を関係者にどう伝えたいか、インサイトをどう活用してどんなアクションを起こしたいか。

## 構成要素

| 要素 | 内容 |
| --- | --- |
| サマリー | 目的、対象（人数や属性）、実施方法、主なインサイトの要約、今後のアクションや推奨事項 |
| 調査概要 | 背景・目的、期間・回数・方法、対象（ペルソナ、セグメント、サンプル数）、スクリプトの概要。どの範囲の情報から結論を導いたかを示す |
| ファインディングス | テーマ別・ペルソナ別・時系列・ポジティブ/ネガティブ/アイデアなどの軸でまとめる。客観的データと主観的な考察の両方を入れる |
| ユーザーの声 | 印象的なコメントやエピソードを厳選して引用する。匿名化とプライバシーに注意する |
| インサイトと提案 | 本質的な課題、潜在的なニーズ、競合や代替手段との比較での強み・弱みと、改善提案 |
| アクションプランと優先度 | 短期・中長期の施策、優先度、担当者とスケジュール。ROIとリソースも考えて合意する |

## 形式

| 形式 | 向いている場面 | 注意点 |
| --- | --- | --- |
| スライド | 要点を簡潔にまとめ、口頭で説明しながら共有する | 詳細の網羅には向かない。削りすぎると本質が伝わらない |
| ドキュメント | 詳細や注釈、引用を網羅し、後から検索・再利用する | 分量が増えて全体をつかみにくい |
| ダッシュボード（Miro、Notion、Confluenceなど） | チームで同時に閲覧・編集し、コメントやタスク管理をする | ツールに慣れない人が戸惑う。情報設計が整っていないと探しにくい |

## プロセス：レポートを作る

<Steps>
  <Step title="直後に整理する">ヒアリング直後に、仮説やキーワードごとにタグを付ける</Step>
  <Step title="複数の視点で分析する">定量・定性・ペルソナ別・機能や利用シナリオ別に見る</Step>
  <Step title="図表で示す">グラフ・表・図解で情報を集約し、詳細はテキストで補う</Step>
  <Step title="期待をすり合わせる">ステークホルダーに求められている情報やフォーマットを事前に確認する</Step>
</Steps>

<Note title="目安">伝わるレポートは、ペルソナを強調して物語性を持たせ、ビジュアルマップで全体像を見せ、インサイトの優先度とインパクトをチャートで示し、施策を試した結果とのつながりを可視化している。</Note>

## ステークホルダーへの報告

典型的な構成は「背景と目的 → ユーザー像やターゲット → ヒアリングの方法 → 主要なインサイト → 示唆・提案 → 次のステップ」。

- 冒頭で「本日の目的」と「期待するアウトプット」を伝える
- 結論を先に出し、結論と対応策をセットで示してから、詳細データやユーザーの声で補う
- 相手によって強調するポイントを変える（法務なら規約やセキュリティ、営業なら獲得数やアップセル）
- ユーザーの生の声や具体的なエピソードで共感を生む
- ネガティブな面だけでなく、ポジティブな評価や好事例も示す
- 数字を優先しすぎて定性的な声を軽視しない
- 質疑応答の時間に余裕を持ち、対立したら「ユーザーにとっての本質的な価値は何か」に立ち返る

## 共有の後

- 優先度の高い課題、必要なリソースと予算、担当部署、期限を決める
- レポートはチーム全員が参照できるナレッジベースに格納する。アクセス権限を設定し、外部共有はユーザーの同意の範囲内で行う
- 用語集や読み方のガイドを用意し、キックオフやワークショップで一緒に議論する
- 同じテンプレートで定期的に更新する。定例でユーザーの声を共有する時間を設けるなど、共有を仕組みにする
- 営業やサポートとも合同でレビューし、「ユーザーは何を求めているか」の共通理解を広げる
