## 原則

- サービスレベルは、サービスを安定稼働させるための基準。性能・データ管理・運用・セキュリティで決める。
- モニタリングには「守り」（安定性）と「攻め」（プロダクト価値の向上）の両方がある。
- インシデントが起きたら、事象の把握とエスカレーションから始める。

## SLAとSLO

| 用語 | 内容 |
| --- | --- |
| SLA（Service Level Agreement） | プロダクトとユーザーの間で交わす、最低限のサービスレベルを保証する契約 |
| SLO（Service Level Objective） | プロダクト側で定めるサービスレベルの目標 |

## ソフトウェア品質の5つの特性（RASIS）

| 特性 | 内容 | 指標の例 |
| --- | --- | --- |
| 信頼性（Reliability） | 障害や不具合による問題の起きにくさ | 平均故障間隔 |
| 可用性（Availability） | 継続して稼働し続ける能力 | サービス時間、稼働率 |
| 保守性（Serviceability） | 障害からの復旧や修正のしやすさ | 平均復旧時間 |
| 完全性（Integrity） | 障害や不具合によるデータの問題の起きにくさ | |
| 機密性（Security） | 外部からの攻撃による問題の起きにくさ | |

## SaaSのサービスレベル項目

| 項目 | 内容 | 例 |
| --- | --- | --- |
| アプリケーション運用 | 使い勝手（可用性・信頼性・性能・拡張性） | サービス稼働率99.9%以上 |
| サポート | 障害対応や一般問い合わせ対応 | 営業時間内（電話）、24時間365日（メール） |
| データ管理 | バックアップなどデータの保証 | バックアップあり、保存期間5年 |
| セキュリティ | 公的認証や第三者評価 | プライバシーマーク取得 |

## インシデント

主な原因は4つ。ソフトウェアのバグ、手運用のミス、外部からの攻撃、トラフィックなどの高騰。

起きたら、まず事象を把握してエスカレーションする。次に影響範囲の把握と、原因調査・復旧方針の整理を並行して進め、対応方針を決めて実行する。

## モニタリング

<Figure src="/figures/n5-2-5-2936.webp" alt="攻めのモニタリングと守りのモニタリング。攻めはKGI・KPI・NSM（ノーススター指標）・行動データなど、プロダクト価値の向上のため。守りはサービスレベルの指標で、安定稼働のため" caption="攻めのモニタリングと守りのモニタリング" />

現状のステータスを確実に把握するために観察すること。ソフトウェアやミドルウェアのログを収集・統合・可視化し、アラートを出す環境を整える。アラートは、サービスレベルの指標にしている項目と閾値をもとに設定する。
