## 原則

- 「プロダクトアウト → マーケットイン」から「マーケットアウト → プロダクトイン」へ。世の中が本当に何を求めているかを追求する。
- 収益規模は「解消する不の大きさ」に比例する。

## サービスブループリントの5つの要素

サービスのプロセスを、顧客から見える部分と見えない部分に分けて描く。

<Figure src="/figures/n1-4-1-2953.webp" alt="サービスブループリントの5つの要素。上から顧客のアクション、オンステージ、バックステージ、サポートプロセスの層があり、有形物が顧客のアクションに添えられる" caption="5つの要素で構成する" />

| 要素 | 内容 | 例（ホテル） |
| --- | --- | --- |
| 顧客のアクション | 顧客がサービスを経験するときの行動 | 予約する、到着する、チェックインする、食事を頼む |
| オンステージ | 顧客と接する従業員の行動 | 荷物を受け取る、宿泊の手続きをする、食事を届ける |
| バックステージ | 顧客と接しない従業員の行動 | 予約情報に基づいて予約する、荷物を部屋に運ぶ |
| サポートプロセス | その他の従業員やシステムを含む行動 | 予約システム、宿泊登録システム、食事を用意する |
| 有形物 | フロントの活動に関わるモノやテクノロジー | ウェブサイト、ホテル外観、部屋の鍵、メニュー、請求書 |

<Figure src="/figures/n1-4-1-2957.webp" alt="サービスブループリントの記入例（ホテル）。宿泊の予約、ホテルに到着、ベルボーイに荷物を預ける、チェックイン、ルームサービスで食事を頼むといった顧客のアクションに対し、オンステージ・バックステージ・サポートプロセスの行動と有形物を並べている" caption="記入例：ホテル" />

| | カスタマージャーニーマップ | サービスブループリント |
| --- | --- | --- |
| 焦点 | ユーザー | サービスのプロセス |
| 効果 | ユーザーの体験を考える | エンジニアがシステムの処理フローを具体的にイメージでき、システム設計に必要な情報が得られる |

## 製品中心からサービス中心へ

商品・サービスをいかに売り込むかを追求する「プロダクトアウト → マーケットイン」から、世の中が本当に何を求めているかを追求する「マーケットアウト → プロダクトイン」へと、必要な視点が変わってきた。

<Figure src="/figures/n1-4-1-2959.webp" alt="顧客視点を保つ考え方。プロダクトアウト→マーケットインは生産者の観点で、商品・サービスをいかに売り込むかを追求する。マーケットアウト→プロダクトインはユーザーの観点で、世の中は何を本当に求めているのかを追求する" caption="生産者の観点から、ユーザーの観点へ" />

| | 製品中心の企業 | サービス中心の企業 |
| --- | --- | --- |
| 目標 | 製品を売ること | 顧客に資すること |
| 価値創出 | 価値は一方向に蓄積する（バリューチェーン思考） | 価値は顧客との協働で生まれる（価値共創） |
| 差別化 | 優れた製品機能・品質、標準化された製造プロセス | 優れた顧客経験・サービス品質、標準化されたサービスプロセス |
| 売り手と買い手 | 取引を成立させることに注力する | 全体のパイを広げることに注力する |
| 考え方 | この製品をどのぐらい買ってもらえるか | この顧客に最も貢献できる方法は何か |
| 戦略的資産 | 設備・在庫・工場などの有形資産 | 人材・ブランド・知的財産などの無形資産 |

サービス中心になるために越えるハードルは6つある。

<Figure src="/figures/n1-4-1-2947.webp" alt="サービス中心の企業になるために越えるべき6つのハードル。1製品中心的なマインドセットから脱却する、2より深い顧客インサイトを見つける、3顧客とサービスを共創する、4サービスをプロセス化するルールを学ぶ、5LTVを高くする考え方でマネタイズする、6より強いチャネルマネジメントを行う" caption="越えるべき6つのハードル" />

顧客との長い関係を築くために、深い顧客インサイトを見つけ、LTVを高くする考え方でマネタイズを設計する。

## 「不」の大きさを測る

<Note title="目安">不の大きさ ＝ 不を抱いている人の数 × 不の深刻さ × 不が生じる頻度。</Note>

インパクトのあるサービスは、小さな輪から段階的に広げて見つける。まず目的をさらけ出し、ペアで仮説を深める。次にラディカルサークル（異なる視点を持つ15〜20人ほどの小さなグループ）で似た仮説と新たな方向を見つけ、最後にビジョンを世に出して多くの人とテストする。

<Figure src="/figures/n1-4-1-2949.webp" alt="サービスのインパクトの見つけ方（イノベーションを起こすプロセス）。私が目的をさらけ出し、ペアで仮説を深め、ラディカルサークルで似た仮説を見つけ、傍観者とともに新たな方向を見つけ、人々とビジョンをテストする" caption="私 → ペア → ラディカルサークル → 人々へと広げる" />

## MVPで検証する

| レベル | やり方 |
| --- | --- |
| 1 | 見せるだけで検証できるコンセプトを使う（手書きの企画でも良い）。想定顧客を人力で集め、課題に手探りで対応する |
| 2 | 「オズの魔法使い」で、需要と解決策の有効性を検証する（SNSやブログなど既存サービスを組み合わせる） |
| 3 | 初めてオリジナルのビジュアルを作る。Webならトップだけ、デバイスなら外側のUIだけで、動かさず見せるだけで良い |

### オズの魔法使い

ユーザーに見える部分は完成版のようにシステム化されているように見せ、中身の処理は人が手で行うプロトタイピング手法。注文が入るたびに担当者が商品を買いに行って手作業で発送するなど、手動でできる部分は手動で行う。

- 必要最低限のリソースでリリースできる（最初はプロダクトを作らない）
- 運用しながら見つけたボトルネックを優先して開発するので、無駄が少ない
- 「なぜ作るのか」の説明が十分にあるので、エンジニアも納得できる
- 作ったものが確実に使われる
