## 原則

- <Mark>**ビジネス職経験のある人は「コミュニケーション」を強みにする。言語化はPMの大事なスキル。**</Mark>
- プログラミングとデザインは、実務経験がなくても自分で作ったり試したりする。作れるレベルでなくてよい。エンジニアとデザイナーが何をしているかイメージできることが大事。
- 開発チームから信頼されるPMには、技術・デザインへのリスペクトがある。

## 強み

| 強み | 内容 |
| --- | --- |
| ユーザーとのコミュニケーション | ヒアリングを抵抗なく実施できる人が多い |
| 交渉・合意形成 | 上司やステークホルダーとの交渉や合意形成が得意な人が多い |
| ビジネス戦略の理解 | 事業を成長させる戦略から、プロダクトの戦略を一気通貫で考えやすい |
| 事業開発との連携 | 事業とプロダクトをつなげて考えやすい |
| セールス・マーケティングとの連携 | 課題解決に欠かせない他部署との連携がしやすい |

PMスキルを磨いたら、事業開発スキルも磨くとキャリアの大きな強みになる。

## 弱み

| 弱み | 内容 |
| --- | --- |
| 技術の理解不足 | 実現不可能な機能を考えてしまうことがある |
| デザインの理解不足 | 課題解決のためではなく、自分の好きなデザインにこだわりがち |
| 開発プロセスの理解不足 | プログラムを書いてから実装されるまでの流れがイメージしにくい |
| 短期的なKPIだけを追う | 目先のKPI達成を追い、本質的なプロダクトの価値を忘れがち |
| ユーザーの意見に振り回される | ユーザーに近いゆえ、1つの意見を重視しすぎて言いなりに開発しがち |

## するべきこと

| 行動 | 内容 |
| --- | --- |
| プログラム・デザインを作ってみる | 手を動かすと、開発者の仕事を具体的に理解できる |
| 技術・デザインのトレンドを把握する | ビジネスと同じく、技術とデザインにもトレンドがある |
| エンジニア・デザイナーに頻繁に相談する | 会話するほど開発の知識が増える。慣れないうちは相談の回数を増やす |
| メインユーザーを定義する | あらゆるユーザーに対応するのではなく、メインユーザーを具体的に決める |
| 機能を選択と集中する | メインユーザーの課題解決に役立つ機能だけを選ぶ。機能開発はお金と時間がかかる |

<Caution>開発が大変な機能を勝手に決めて押しつけると、開発チームの信頼を失う。</Caution>

## 強みを掛け算する

セールス × PM、マーケティング × PM、CS × PM、バックオフィス × PM、事業開発 × PMのように、PMスキルと掛け算できる自分の専門性を決める。1つ専門性があると相乗効果が得られ、キャリアアップしやすい。
