## 原則

- 理想は、他の人がPRDさえ読めば行動できる状態。
- いきなり機能から考えてはいけない。プロダクトの存在目的は「ユーザーの課題を解決すること」で、すべての機能はこの目的から逆算する。
- 目的と機能を対応させる（要件トレーサビリティ）。目的を達成しない・関係しない機能は無駄な機能。

## 構成

| 部 | 項目 |
| --- | --- |
| 1. 目的 | 全体概要／課題の背景／対象ユーザー／重要である理由 |
| 2. 機能説明 | 解決策の仮説／機能要求／UX要求／非機能要求／関係する機能・チケット |
| 3. リリース計画 | チケットの優先順位／リリーススケジュール／デザインドキュメント／効果計測KPI |

## 1. 目的

この機能で解決する課題や、達成したい状態を言語化する。

| 項目 | 書くこと |
| --- | --- |
| 全体概要 | 機能の概要と解く課題を200文字前後で要約する。後から開発チームに入った人でも分かるように |
| 課題の背景 | なぜこの機能が必要なのか。背景となる課題とファクトを書く。推測や思い込みは書かない |
| 対象ユーザー | 誰が持っている課題なのか。Super Specific Whoを言語化する。具体的に誰か判断できないと、作るべき機能を決められない |
| 重要である理由 | 作るべき機能は山ほどある中で、この機能の優先度が高いと判断できる理由。重要だと判断できなければ、実装しないこともある |

## 2. 機能説明

目的達成のために最適な機能を考える。

| 項目 | 書くこと |
| --- | --- |
| 解決策の仮説 | どんな機能があれば課題が解決できるか。ユーザーと課題の解像度が高くなければ書けない。課題が抽象的だと解決策も抽象的になる |
| 機能要求 | 具体的な機能を洗い出す。技術的な話より機能の概要が中心。例：記事を投稿する、コメントする、投票する、一覧で表示する |
| UX要求 | どんなUIで、どんな流れで使うのか。主にデザイナーに伝える。決めないと機能だけあっても使いこなせない |
| 非機能要求 | 機能を支えるために必要なこと。主にセキュリティ、運用保守、拡張性 |
| 関係する機能・チケット | 影響する範囲や、関連して開発するチケット。1つの機能が他に大きく影響するときは、エンジニアに相談しつつプロダクト全体を俯瞰する |

<Caution>ほとんどのPMが機能から考え始めてしまう。解決策は思いつきで決めず、課題から逆算する。リリースして効果がないなら、機能を引っ込める決断も時には必要。</Caution>

## 3. リリース計画

| 項目 | 書くこと |
| --- | --- |
| チケットの優先順位 | 他に開発すべき機能と比べてどれくらい優先するか。すべてを「最優先」にしない。課題を効果的に解決できる順番がそのまま優先順位になる。大きな機能は分割してリリースする |
| リリーススケジュール | いつリリースするか |
| デザインドキュメント | 実装のためのワイヤーフレームやデザインのURL。UI次第で機能の良し悪しは大きく変わる |
| 効果計測KPI | 課題が解決できたかを測る定性・定量のKPI。事業が健全に成長するための最も大事な指標「センターピン」になるKPIを決める。リリース後に違っていると判断したら都度修正する |
