## 原則

- <Mark>**測定は、指標を定める → 測り方を定める → 想定との差を判断する → 改善する、の順で回す。**</Mark>
- ダッシュボードで閾値を超えたものを直感的に察知できるようにする。
- 遅れているときだけでなく、前倒しや余剰のときも打ち手を考える。

## 測定指標

| 分類 | 主な指標 |
| --- | --- |
| 成果物 | 不具合数・解決数・原因別件数、パフォーマンスの尺度（容量、精度、信頼性、効率）、技術的な要求事項の完成率 |
| デリバリー | 仕掛かり作業、リードタイム（バックログ発生から完了まで）、サイクルタイム（1タスクの完了まで）、待ち行列のサイズ、バッチサイズ、プロセス効率（付加価値を生む時間の比率） |
| ベースラインとの比較 | 開始日・終了日、工数と所要時間、スケジュール差異と効率指数、フィーチャー完了率、実コスト（バーンレート）、コスト差異と効率指数 |
| 資源 | 計画した資源・資源コストと実績の比較 |
| 事業価値 | 費用便益率、計画した利益と実際の利益、ROI、正味現在価値 |
| ステークホルダー | NPS、ムードチャート（チームの日々の気持ち）、士気・モチベーション（定量アンケート）、離職率 |
| 予測 | 残作業の見積もりと効率指数、完成時総コストの見積もりと差異、回帰分析、スループット分析（一定期間に完了する項目数から完了日を予測） |

## 測定ツール

| 形式 | 使い方 |
| --- | --- |
| ダッシュボード | スケジュール、採用、開発生産性、予算、不具合などのステータスとコメントを見える化する。閾値を外れたら直感的に危機を察知できる |
| バーンアップチャート | 作業の全体量と完了した作業量を時系列で追い、ベロシティに異変がないかを見る。完了量が極端に減ったら問題を疑う |

## 閾値を超えたときのアクション

| 対象 | 状況 | アクション |
| --- | --- | --- |
| 計画 | 遅れている | ステークホルダーと交渉し、品質要求の制限、予算追加・増員、スケジュールの再設定、スコープの縮小のいずれかで調整する |
| 計画 | 前倒ししている | 今後のボトルネックを探して解消する。人員や予算を他の重要事項に回す。品質向上や日程の前倒しを検討する |
| 開発生産性 | 下がっている | 体調不良や家庭事情なら稼働調整やリモートワーク。仕様の複雑さや技術難易度なら専門家の支援や作業量の変更 |
| 開発生産性 | 上がっている | チームが学んだことを共有し、他チームに横展開する。他のボトルネックに先回りする |
| 成果物 | 不具合が多い | テスト項目・体制・計画を見直す。原因を特定し、回避するチェック項目を足す |
| 成果物 | 性能が想定以上 | 余分なコストがかかる過剰な性能でないかを調べ、性能テストの条件を調整する |
| 予算 | 不足している | 要員の削減、計画の中断、範囲の限定。緊急性が高ければ撤退も |
| 予算 | 余っている | 追加プロジェクトの検討、利益確保やリスクヘッジのための予算プール |
| 採用・要員 | 調達が遅れている | スケジュールの再設定や範囲の限定などQCDSを調整する。必要スキルの調整や技術の再選定 |
| 採用・要員 | モチベーションが下がっている | 責任の範囲を限定または拡大し、権限移譲で自立を促す。報酬や評価を改善する |
