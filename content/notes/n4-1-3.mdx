## 原則

- <Mark>**いきなり完璧なプランを作るより、仮説を立てて短いサイクルで検証するほうが効率的。**</Mark>
- 仮説が間違っていれば修正し、正しければ洗練させる。短期間で実行と検証を繰り返すほど、精度の高い解決策に到達しやすい。
- 「仮説が外れるのは当たり前」という認識をチームで共有する。

## 課題解決のスパイラル

<Steps>
  <Step title="仮説を立てる">問題に対する解決策の仮説を立てる</Step>
  <Step title="検証する">プロトタイプを使って仮説を検証する</Step>
  <Step title="学ぶ">検証結果から学びを得る</Step>
  <Step title="修正する">学びを基に仮説や解決策を修正する</Step>
</Steps>

プロトタイプは、仮説を具体的な形で確かめるためのもの。ユーザーが使える・体験できるデモや簡易モデルで、本番の実行に先駆けて解決策の妥当性を検証する試作品という位置づけ。

## 問題設定とゴールを明確にする

問題が曖昧だったり目的がはっきりしなかったりすると、仮説は的外れになりやすい。

- **ステークホルダーを整理する**：課題を抱えているのは顧客か、社内のメンバーか、一般ユーザーか。それぞれの立場から見た問題点を挙げる。
- **ファクトを集める**：売上や満足度のような数値だけでなく、インタビューやアンケートの定性情報も集めると、隠れたニーズや背景が見える。
- **ゴールを言語化する**：どんな状態なら成功か。「売上が一定の数字に達する」「開発期間を〇%短縮する」など、定量・定性で置く。
- **ゴールと問題の因果を確かめる**：ゴールが本当に解くべき問題と結びついているかを再確認する。

## 仮説を作る考え方

| 手法 | 内容 |
| --- | --- |
| 5 Whys | 「なぜ」を繰り返して根本原因に迫る。例：満足度が低い → サポートが遅い → 都度情報を確認している → 顧客情報が一元化されていない → 連携システムがない → 部署間の連携がうまくいっていない |
| SCAMPER法 | 既存のサービスや仕組みに、代替・結合・応用・修正・転用・削除・再配置の観点で切り口を与える |
| 逆転の発想 | 「顧客満足度を上げるには」を「下げるには」に反転して考え、出た解決策を再び反転して新しい視点を得る |

<Caution>経験則だけに頼るのも、データだけを鵜呑みにするのも危険。「このデータはどの程度信頼できるか」「過去の類似事例と今回は何が違うか」と、常に批判的に考える。</Caution>

## 検証の進め方

一度にすべての仮説を大規模に検証するのは非効率。**小さく早く始めて**、早期にユーザーの反応を得て方向を修正し、改善を繰り返す。

| 方法 | 内容 |
| --- | --- |
| MVP | 最小限の機能を持つ製品を公開し、使ってもらいながら反応を得る |
| A/Bテスト | AとBを並行して試し、どちらが優位かを検証する |
| インタビューと観察 | プロトタイプを試してもらい感想を聞く。使っている様子を見ると、本音や潜在ニーズが見える |
| 定量データ | アクセス解析や行動ログを追い、仮説どおりに行動や数値が変わっているかをKPIでウォッチする。データは素直に受け止める |

## プロセス：プロトタイプを設計する

<Steps>
  <Step title="目的と検証項目を整理する">何を検証したいのかを決め、評価指標をあらかじめ設定する</Step>
  <Step title="必要最小限の機能・デザインを洗い出す">コアとなる体験を優先する。紙とペンから始める</Step>
  <Step title="作る">素早く作り、テストし、改良する</Step>
  <Step title="テスト環境を整える">実際のユーザーに触ってもらえる環境を用意する</Step>
</Steps>

## 事例：ECサイトのカート放棄

| 段階 | 内容 |
| --- | --- |
| 課題 | カートに入れたまま放置される。原因は「決断に迷う」「送料や返品の条件が分かりづらい」といった不安 |
| ゴール | カート放棄率を〇%削減し、購入完了率を上げる |
| 仮説 | A：送料・返品ポリシーを明示すれば購入率が上がる／B：チャットボットでリアルタイムに質問に答えれば不安が解消する／C：レビューを目立つ位置に置けば決断を後押しする |
| プロトタイプ | A：カート画面に送料・返品方法・到着予定日のバナー／B：よくある質問に自動応答するチャットボット／C：レビュー欄を購入ボタンの近くへ |
| テスト | 訪問者の一部にだけ新デザインを出してA/Bテストし、ヒアリングも行う。購入完了率、滞在時間、離脱率を測る |
| 結果 | Aは購入率が向上、Bは影響が小さかった。ただし「チャットボットより店舗スタッフと話したい」という声が多かった |

## 注意点

| 注意点 | 内容 |
| --- | --- |
| 仮説の数を絞る | 実際に検証するのは2〜3案程度が現実的 |
| 外れたことを責めない | 外れるのは当たり前という文化をつくる |
| 定量と定性の両面で評価する | 定量データは結果を示し、定性データはその背景にある理由を補う |
| PDCAを素早く回す | 計画・実行・評価・改善を短いスパンで回す |
