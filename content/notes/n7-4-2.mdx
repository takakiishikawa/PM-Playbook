## 原則

- スケジュール計画は一度立てたら終わりではない。大切なのは、それを前提にした計画運用。
- 最も難しいのは期間の見積もり。過去の実績を参考にし、メンバーに聞き、バッファを積む。
- 実行可能なレベルに落とし込む。1〜2週間程度で完了できる単位にタスクを分ける。

## スケジュール計画とは

タスクの洗い出し、担当者の割り当て、作業順序や期間の定義を明確にし、チーム全体と共有すること。誰が何をいつまでにやるかの見通しがはっきりし、ムダな待ち時間、タスクの重複、割り込み作業の混乱を最小限にできる。

| 効果 | 計画不足のリスク |
| --- | --- |
| リスクの早期発見・対策 | タスクの見落とし・遅延 |
| チームの共通認識 | 担当者間の衝突・混乱 |
| 外部ステークホルダーへの説明がしやすい | 品質の低下 |
| モチベーション・責任感の向上 | 不必要なコストの増大 |

## プロセス：スケジュールを作る

<Steps>
  <Step title="目標と範囲を明確にする">何をゴールにどんな成果物を作るか。要件を必須・高・中・低に分け、優先度の高いものからリリースに最低限必要な機能を確実に仕上げる</Step>
  <Step title="タスクを洗い出し依存関係を整理する">可能ならWBSで、誰が見ても内容がイメージできるまで分割する。どのタスクが終わらないと次に進めないかを一覧にする</Step>
  <Step title="リソースと期間を見積もる">過去の類似プロジェクトの実績を参考にし、メンバーに聞いて過少・過大を避ける。合計工数の10〜20%程度のバッファを置くことが多い</Step>
  <Step title="作成して調整する">ガントチャートなどに落とし、マイルストーン、担当者、開始・終了日を明示する。「レビュー → 調整 → 最終確定」を何度か繰り返す</Step>
  <Step title="リスクを評価する">外部要因への依存、メンバーの体調不良・離脱、技術的な不確定要素を挙げ、発生確率と影響度を評価して対応策を用意する</Step>
  <Step title="モニタリングして更新する">進捗を確かめ、ズレたら更新する</Step>
</Steps>

## 管理の手法

| 手法 | メリット | デメリット |
| --- | --- | --- |
| ガントチャート | タスクの期間、進捗、依存関係をひと目で把握できる | タスクが多いと見づらい。細かい変更が多いとメンテナンスが大変 |
| WBS | 洗い出しの漏れがなくなり、全体像と担当を把握しやすい | 実際の開発プロセスと合わないとメンテナンスが煩雑 |
| バーンダウンチャート | スプリントの残作業量の推移を折れ線で示す | |
| カンバンボード | タスクをToDo・Doing・Doneなどに分けて視覚的に管理する | |

アジャイルでは、プロジェクト全体の厳密なスケジュールよりも、1〜2週間の短いスプリントに集中して計画し、レビューを通じて次のスプリントにフィードバックする。

## 陥りやすい罠

| 罠 | 対策 |
| --- | --- |
| 楽観的すぎる見積もり | 開発チームはどうしても短く見積もる。過去の実績と比べて積み上げ、複数人で検討する |
| リソースの過剰な重複 | メンバーごとの実質的な作業可能時間を把握し、他のプロジェクトのピークも考慮する |
| 変更管理が不十分 | 変更の承認フローを明確にし、変更が生じたら必ずスケジュールに反映して影響度を共有する |
| コミュニケーション不足 | 定例やチャットでこまめに進捗を共有し、スケジュール表を常に最新で誰でも見られる状態にする |
